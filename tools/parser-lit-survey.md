## 2. Academic systems — narrative (OMeta, Racket `#lang`, SweetJS)

I did **not** spend crawl budget on these three (per the priority note in the task prompt) and work from background knowledge. They all operate at a different level from SPEC-032 — they are compile-time, in-process extensions to the host parser — but two ideas are portable:

**Reader macros / extensible parsers share one lesson: extensions must declare their extent.** Racket `#lang` lines scope a reader change to one file. OMeta grammars compose by inheritance (`SmallTalk <: Parser`). SweetJS macros declare their pattern-match shape so the compiler can decide enclosure. The common thread is that *runtime-extensible parsing only stays sane when each extension says, up front, what syntactic niche it occupies*. SPEC-032's path-glob + frontmatter predicate + content probe is the practical analogue of "what niche does this extension cover", and is more conservative than e.g. markdown-it's model (any plugin can edit any token).

**Hygiene.** SweetJS and Honu (Flatt et al., "Macros that Work Together" — *JFP* 2012) invest heavily in hygienic macro expansion: extensions cannot accidentally capture or shadow names defined in the host program. For a Markdown system this translates to *namespace isolation for user-visible identifiers* — both for template variables exposed by hooks (SPEC-032 correctly reserves `page.ext.<extension_id>`) and for anchor/id/class strings written into HTML. Honu/Racket's insight is that enforcement is cheaper when the host allocates the namespace, not when it trusts the extension to prefix things.

**Academic mechanism, not portable.** OMeta's PEG semantics, Racket's reader/expander split, and SweetJS's hygiene are all compile-time machinery that doesn't map onto out-of-process JSON hooks. Don't try to port the mechanism; port the *discipline*: declared scope, allocated namespaces, reproducible composition order.

## 3. Borrowable ideas for SPEC-032 (concrete improvements)

### 3.1 Split "binary version" from "AST schema version"

**Pandoc does this and it is the single most important protocol-hygiene decision they made.** `PANDOC_VERSION` changes on every release; `PANDOC_API_VERSION` only changes when `pandoc-types` (the AST schema) changes. A filter written against `PANDOC_API_VERSION = {1,17,3}` continues to work across 2.7.3 → 2.11.1 → 2.17 binary upgrades. ([filters.html](https://pandoc.org/filters.html), [lua-filters.html](https://pandoc.org/lua-filters.html) `PANDOC_VERSION` / `PANDOC_API_VERSION` sections.)

**For SPEC-032:** Every hook invocation should expose both `ZETL_VERSION` (the binary) and `ZETL_AST_VERSION` (the JSON-schema semver). Hooks declare a required `ast_version: ">=1.0 <2"` (npm-style) in their manifest. This lets zetl evolve unrelated features (graph store, history, web server) without breaking hooks, and lets you ship AST-breaking changes on a slower, louder track.

### 3.2 Capability probe before the real invocation

mdBook's "run twice" pattern — first with `supports <renderer>` returning exit 0/1, then with real input — means the preprocessor declares its applicability before the build loop pays the cost of serialising the full book. ([for_developers/preprocessors.html](https://rust-lang.github.io/mdBook/for_developers/preprocessors.html))

**For SPEC-032:** A `supports` / `--probe` argv mode lets a hook short-circuit itself based on the current output format, feature flags, or zetl version. Cheap to implement, cheap to run, provides a useful diagnostic surface (`zetl hooks check` can call every hook's probe).

### 3.3 Explicit ordering constraints (`before` / `after`)

mdBook: `before = ["linenos"]`, `after = ["links"]`, equal priority → sorted by name, cycles detected and errored. ([format/configuration/preprocessors.html](https://rust-lang.github.io/mdBook/format/configuration/preprocessors.html))

**For SPEC-032:** "Pipeline order = CLI/config order" (Pandoc's model) is OK for three-letter pipelines but becomes opaque with ten hooks. Let extension authors declare ordering constraints at the stage level (`stage: transform, after: ["wikilinks"]`) and let zetl topologically sort. Keep "pipeline order is the config order" as the default for zero-constraint hooks so simple setups stay simple.

### 3.4 `optional: true` for missing hooks

mdBook: `[preprocessor.example] optional = true` demotes a missing executable from error to warning. ([format/configuration/preprocessors.html](https://rust-lang.github.io/mdBook/format/configuration/preprocessors.html))

**For SPEC-032:** Let `zetl.toml` mark a hook as optional so `git clone && zetl build` doesn't fail on a contributor's machine that lacks an optional Python dependency. Especially important given hooks run out-of-process with language-specific runtimes (Python, Node, Ruby).

### 3.5 Declarative selection — function-table-keyed-by-node-type

Pandoc Lua filters' dispatch by element name (`{ Strong = fn, Para = fn, Inline = fallback, Block = fallback }`) is **dramatically** less error-prone than "walk the whole tree and filter by `type`." ([lua-filters.html](https://pandoc.org/lua-filters.html) "Lua filter structure")

**For SPEC-032:** The transform-stage helper libraries should ship a top-level dispatch wrapper that takes a dict keyed by node type (and `Inline` / `Block` fallbacks) and invokes the appropriate function for each node — analogous to `pandocfilters.toJSONFilter`. The low-level "here's an AST, go visit it yourself" path should remain available but shouldn't be the 80% path. This complements the spec's file-level selector (glob + frontmatter + probe) with a node-level selector.

### 3.6 Sequence-level hooks alongside element-level hooks

Pandoc's `Inlines(inlines)` and `Blocks(blocks)` filter entries exist because "for some filtering tasks, it is necessary to know the order in which elements occur in the document. It is not enough then to inspect a single element at a time." ([lua-filters.html](https://pandoc.org/lua-filters.html))

**For SPEC-032:** The `transform` stage should offer both per-node and per-sequence dispatch. Plugins that need to look at *"this Heading followed by this Paragraph"* (e.g. to implement callouts, TOC extraction, or smart-quote-around-em-dash rules) need list-level access or they degenerate into correctness-destroying single-pass state machines.

### 3.7 `env` / shared-data channel between hooks

unified's `processor.data(key, value)` and markdown-it's `env` parameter both exist because hooks on the same pipeline frequently need to share information (one computes, the other consumes). ([unified readme](https://github.com/unifiedjs/unified), [markdown-it architecture](https://github.com/markdown-it/markdown-it/blob/master/docs/architecture.md))

**For SPEC-032:** Beyond `page.ext.<extension_id>` (which is the one-way template-facing surface), define a build-scoped key/value store that is passed in every hook invocation and mutated between stages. Example: a wikilink-resolver hook writes `{build_data: {unresolved_links: [...]}}`, a report-generator hook at post-render reads it. Without this, cross-hook coordination has to happen through frontmatter or filesystem, which is fragile.

### 3.8 Expose reader/writer options to hooks

Pandoc sets `PANDOC_READER_OPTIONS` and `PANDOC_WRITER_OPTIONS` so filters can adapt to e.g. `--columns`, `--tab-stop`, `--standalone`. ([filters.html](https://pandoc.org/filters.html))

**For SPEC-032:** Expose `ZETL_BUILD_OPTIONS` / `ZETL_PAGE_OPTIONS` (as stdin JSON fields or env vars) so hooks can honour `--verbose`, the active theme, whether we're in `serve` vs `build`, `--at` for historical builds, etc. Otherwise hooks will reinvent detection via side-channels.

### 3.9 `script_file` self-locator

Pandoc's `PANDOC_SCRIPT_FILE` lets a filter resolve resources (templates, lookup tables) next to itself. ([lua-filters.html](https://pandoc.org/lua-filters.html))

**For SPEC-032:** The hook invocation should tell the hook its own resolved path. Hooks cannot reliably get this from `argv[0]` (shebang lines, symlinks).

## 4. Design decisions SPEC-032 got right (by established-practice standards)

1. **Three explicit stages named after their substrate** (`pre-parse` text→text, `transform` AST→AST, `post-render` HTML→HTML) — matches unified's **parse / run / stringify** naming and architecture directly ([unified readme](https://github.com/unifiedjs/unified) "parse … run … stringify"). The unified ecosystem is the most battle-tested plugin ecosystem in this problem space (thousands of remark/rehype plugins) and they landed on exactly this three-stage shape.
2. **Out-of-process hooks over line-delimited JSON** — this is Pandoc's exact model, and Pandoc's success at growing filters in Python, Haskell, Ruby, Node and Perl ([filters.html](https://pandoc.org/filters.html) "Supported interpreters") is the strongest evidence that JSON-over-stdio is the right protocol for a Markdown-processing system that wants multi-language extensibility. mdBook made the same choice with the same justification ([for_developers/preprocessors.html](https://rust-lang.github.io/mdBook/for_developers/preprocessors.html) "The fact that mdBook utilizes stdin and stdout to communicate with the preprocessors makes it easy to implement them in a language other than Rust").
3. **Helper libraries for Python and JS that hide the protocol** — directly mirrors Pandoc's `pandocfilters` (Python) and `Text.Pandoc.JSON` (Haskell) ([filters.html](https://pandoc.org/filters.html) "we can use Python … `toJSONFilter(behead)` walks the AST"), which is the single biggest reason Pandoc's filter ecosystem grew.
4. **Zetl-defined AST JSON schema (CommonMark subset + wikilink/embed/frontmatter extensions)** rather than adopting mdast or pandoc-types wholesale — this is the right call because mdast lacks wikilinks (mdast's extensions list covers GFM, frontmatter, MDX, not wikilinks — [mdast spec](https://github.com/syntax-tree/mdast#extensions)) and bolting them in as a vendored superset would break `@types/mdast` users. Having your own schema also gives you control over the versioning story (see §3.1). markdown-it made the analogous choice with tokens vs an AST: "Why not an AST? It's not needed for our tasks. We follow the KISS principle." ([markdown-it architecture](https://github.com/markdown-it/markdown-it/blob/master/docs/architecture.md))
5. **First-class file selection (globs + frontmatter + content probe)** — no comparable system has this; Pandoc matches everything, mdBook walks all chapters, markdown-it applies every rule to every token. The closest precedent is mdBook's renderer-scoped preprocessors (`renderers = ["html"]`) which is strictly coarser. SPEC-032's declarative selector is genuinely an improvement over prior art and will make hooks cheaper at scale.
6. **Reserved template-variable namespace (`page.ext.<extension_id>`)** — Pandoc and mdBook expose *no* template surface from filters/preprocessors; unified/markdown-it offer `file.data`/`env` with no namespace discipline. Having a reserved, extension-scoped namespace up front avoids the `data.myPlugin` collision-by-convention that the JS ecosystem lives with.

## 5. Gotchas SPEC-032 should explicitly address

1. **Version-drift handling.** mdBook emits a warning when plugin binary version ≠ current mdBook version and keeps going ([for_developers/preprocessors.html](https://rust-lang.github.io/mdBook/for_developers/preprocessors.html) `handle_preprocessing` example). SPEC-032 should spell out what happens when `ZETL_AST_VERSION` and the hook's declared `ast_version` don't match: hard-fail (default), warn-and-continue (opt-in), or fail-open. Without an explicit policy, implementers will pick differently per language-binding.
2. **Executable-bit fallback.** Pandoc's filter loader guesses an interpreter from file extension if the executable bit is missing ([filters.html](https://pandoc.org/filters.html) "Supported interpreters" — `.py→python`, `.js→node`, …). Decide: do zetl hooks require the executable bit, or do we replicate the extension-to-interpreter map? Replicating is friendly; requiring the bit is unambiguous. Either way, the spec should pick one.
3. **Round-tripping at `pre-parse` is treacherous.** mdBook docs: "chapter.content is just a string which happens to be markdown. While it's entirely possible to use regular expressions or do a manual find & replace, you'll probably want to process the input into something more computer-friendly." ([for_developers/preprocessors.html](https://rust-lang.github.io/mdBook/for_developers/preprocessors.html)) Document explicitly that `pre-parse` hooks operate on *raw markdown text* and any non-trivial edit risks breaking the downstream parse. Name at least one valid use case (e.g. template-variable expansion of `{{ page.title }}`) and one anti-pattern (e.g. "do not try to add emphasis from pre-parse — write a `transform` hook").
4. **Return-type contract at `transform`.** Pandoc is strict: return nil, same-type element, or list-of-same-type. Violations error out. ([lua-filters.html](https://pandoc.org/lua-filters.html) "Pandoc will throw an error if this condition is violated.") SPEC-032 should spell out what happens when a `transform` hook returns a `Heading` where a `Text` was expected — reject and abort the build, reject and skip the hook, or silently corrupt the tree? Pick one and document.
5. **Cycle detection for ordering constraints.** If SPEC-032 adopts `before`/`after` (see §3.3), say explicitly that cycles are a build error, following mdBook: "Any infinite loops will be detected and produce an error." ([format/configuration/preprocessors.html](https://rust-lang.github.io/mdBook/format/configuration/preprocessors.html))
6. **Sandboxing / trust model.** *None of the priority-1 systems discuss this* — hooks are arbitrary executables by design. If zetl is aimed at users running untrusted third-party hooks (plausible for a KM tool sharing vaults), the spec should at least flag this as an out-of-scope concern so implementers don't assume filesystem/network isolation is coming.
7. **Error surfacing.** Pandoc writes filter errors to stderr and exits the build. mdBook ditto. markdown-it and unified throw JS exceptions. SPEC-032 should define: stdout is JSON, stderr is human-readable logs forwarded to zetl's output, non-zero exit aborts the build (unless `optional=true`). State this explicitly.
8. **Frozen vs mutable state.** unified's frozen-processor gotcha ([unified readme](https://github.com/unifiedjs/unified) `data()` signatures) is a language-specific artifact but the underlying principle — once the pipeline is compiled, `.data()` is read-only — applies to zetl's build-scoped store too. Say so.
9. **`pre-parse` is whole-file or line-chunked?** Pandoc's filters always get the whole document; mdBook ditto. Streaming isn't a thing in any of the priority-1 systems. If SPEC-032 is whole-file-only, say so; if it contemplates streaming, the JSON-per-line protocol becomes a framing concern (which Pandoc avoids with single-blob JSON).
10. **Traversal-order control.** Pandoc added topdown traversal in 2.17 because "it is sometimes more natural to traverse the document tree depth-first from the root towards the leaves" ([lua-filters.html](https://pandoc.org/lua-filters.html) "Topdown traversal") — and this turned out to be a breaking-ish change for filters that relied on typewise order. Pick a default traversal order *now* (typewise is pandoc's, topdown is intuitive) and document it as part of the AST contract, not an implementation detail.

## 6. Executive summary (≤500 words, drop-in for SPEC-032 "Prior art" section)

SPEC-032's three-stage render-hook system sits squarely inside a well-established design space, and its main shape choices are validated by prior practice.

**The core protocol — out-of-process hooks communicating over line-delimited JSON — is exactly Pandoc's filter model** ([Pandoc filters](https://pandoc.org/filters.html)) and mdBook's preprocessor model ([mdBook preprocessors](https://rust-lang.github.io/mdBook/for_developers/preprocessors.html)). Both ecosystems cite multi-language extensibility as the key payoff, and both grew healthy plugin ecosystems on the strength of it. Pandoc explicitly supports five extension languages through an interpreter fallback table; mdBook's docs devote a section to Python plugins. SPEC-032's decision to ship Python and JS helper libraries mirrors Pandoc's `pandocfilters` and `Text.Pandoc.JSON`, which are widely credited as the lubricant that made Pandoc's filter ecosystem scale.

**The three-stage pipeline — `pre-parse` text→text, `transform` AST→AST, `post-render` HTML→HTML — is the same shape as unified's parse / run / stringify model** ([unified](https://github.com/unifiedjs/unified)), which powers remark, rehype, and retext. Unified is the largest plugin ecosystem in this space (thousands of published plugins) and converged on exactly this three-phase factorisation. markdown-it by contrast uses a four-chain token-stream model; its own docs defend this as a KISS alternative ([markdown-it architecture](https://github.com/markdown-it/markdown-it/blob/master/docs/architecture.md)) but acknowledge it costs you the AST surface area third-party tooling expects.

**SPEC-032's novel contributions** — first-class file selection (globs + frontmatter + content probe) and a reserved `page.ext.<extension_id>` template namespace — are genuine improvements over prior art. No priority-1 system offers declarative pre-dispatch file scoping (Pandoc, mdBook, markdown-it all apply every registered extension to every node); the closest precedent is mdBook's coarse `renderers = ["html"]` binding. The namespaced template surface is without precedent: Pandoc and mdBook expose no template variables from filters/preprocessors, and unified's `file.data` / markdown-it's `env` have no namespace discipline, leading to collision-by-convention.

**The spec should borrow six concrete practices from prior art before going to `approved`:**

1. **Split binary version from AST-schema version** — Pandoc exposes `PANDOC_VERSION` and `PANDOC_API_VERSION` separately so filters survive non-AST-breaking upgrades ([Pandoc Lua filters](https://pandoc.org/lua-filters.html)).
2. **Capability probe before real invocation** — mdBook's `supports <renderer>` / exit-code pattern ([mdBook dev guide](https://rust-lang.github.io/mdBook/for_developers/preprocessors.html)).
3. **Explicit `before` / `after` ordering with cycle detection** — mdBook's ordering system ([mdBook config](https://rust-lang.github.io/mdBook/format/configuration/preprocessors.html)).
4. **`optional: true` for missing hooks** — demotes to warning, mdBook pattern.
5. **Declarative node-type dispatch** in the helper libraries — Pandoc Lua filters' `{ Str = fn, Heading = fn, Inline = fallback }` model is dramatically less error-prone than visit-all-and-filter ([Pandoc Lua filters](https://pandoc.org/lua-filters.html)).
6. **A shared build-scoped key/value channel between hooks** — unified's `processor.data()` and markdown-it's `env` both exist because cross-hook coordination through frontmatter/filesystem is fragile.

**Finally, the spec should address ten gotchas that every prior system either solved or got burned by** — the most important being version-drift policy (hard-fail vs warn-and-continue), `transform` return-type enforcement, sandboxing/trust posture, and a named default traversal order. These are in §5 with citations.
