# Tier 1 Adversarial Crypto Review — Rust Implementation

## Reviewer Context

- Model: `claude-opus-4-7[1m]`, fresh session.
- Artefacts reviewed at the HEAD of `hence/cap-tier1-review-crypto-v1`:
  - `src/cap/sign.rs` (910 L)
  - `src/cap/pad.rs` (260 L)
  - `src/cap/derivation.rs` (323 L)
  - `src/cap/age_encrypt.rs` (358 L)
  - `src/cap/genkey.rs` (541 L)
  - `src/cap/invite.rs` (450 L)
  - Adjacent: `src/cap/recipients/parsing.rs::is_valid_cohort_id`, `src/main.rs::cmd_cap_invite` effectful-shell wiring.
- Locked crate versions: `age 0.11.2`, `ed25519-dalek 2.2.0`, `x25519-dalek 2.0.1` (features: `static_secrets`, `zeroize`), `hkdf 0.12.4`, `hmac 0.12.1`, `sha2 0.10.9`, `zeroize 1.8.2`, `rand_core 0.6.4`.
- Companion spec review (Tier 2) is at `.hence/reviews/cap-tier2-2026-04-20.md`; this review does not re-litigate spec-level findings except where a test pins the flagged behaviour at code level.

## Severity key

- **S1** — blocker; code is cryptographically broken or defeats a claimed mitigation. Must be fixed before merge.
- **S2** — material gap; silent reliance on an assumption that the code does not itself enforce, or a zeroisation/no-log discipline that is locally violated. Should be fixed before merge; can be parallelised with other v0.5.x work if the fix is non-trivial.
- **S3** — clarity, robustness, or regression-defence hygiene. Worth fixing; does not block merge.

Priority areas per the task brief: **(a)** age usage, **(b)** Ed25519 signing layer, **(c)** X25519 padding key-discard, **(d)** HKDF `info` parameter separation, **(e)** WebAuthn PRF salt construction. Cross-cut: key material handling (zeroisation, no-log), padding pubkey generation that verifiably discards privkeys, signature byte-range correctness, challenge randomness.

## Summary

Zero S1 findings. Three S2 findings, eleven S3 findings.

The cryptographic construction is sound:

- Ed25519 signing uses `verify_strict` (rejects non-canonical R/S, small-order A); deterministic per RFC 8032.
- Ed25519 signatures are applied to the raw age-ciphertext byte range as CON-3404 prescribes. Determinism is exercised directly by `envelope_is_byte_stable_under_fixed_inputs` and `signatures_are_deterministic`.
- X25519 padding scalars are generated by `StaticSecret::random_from_rng(rng: CryptoRng)`, wrapped in `EphemeralPaddingSecret(StaticSecret)` which `#[derive(ZeroizeOnDrop)]`s. The wrapper is `drop`-ed inside the per-iteration loop before the next allocation. `ephemeral_padding_secret_is_zeroize_on_drop` pins the marker at compile time — the "verifiable discard" ADR-3413 asks for.
- Padding pubkey structural indistinguishability (REQ-3422) is enforced at two levels: (i) same `-> X25519 ` stanza prefix in the age header (`header_stanzas_are_all_x25519`); (ii) same byte-shape (32 bytes) as real recipients.
- HKDF `info` separation is clean: `ztl/path-cap/v1/`, `ztl/tofu-wrap/v1`, `ztl/hardened-identity/v1` are all distinct byte strings; the triple is exercised together in `wrap_key_deterministic_and_distinct_from_identity`.
- WebAuthn PRF salt construction has no Rust-side surface — that composition is shim-side. The Rust core only consumes `prf_output` as HKDF IKM. This review therefore has nothing to say about the `SHA-256("ztl/webauthn-prf/v1/" || rp_id || "/" || cohort_id)` composition itself; Tier 2 S3-01 remains the canonical place for that discussion.
- Challenge randomness is not a Rust concern (shim generates the 32-byte WebAuthn challenge via `crypto.getRandomValues`). Rust-side randomness (grant-id bodies, cohort salt_stable, invite keypairs, padding scalars, signing keys) all route through `rand_core::OsRng` (which is `getrandom`-backed). Two back-to-back `generate()` calls in `genkey::tests::two_calls_produce_distinct_secrets` pins the non-deterministic path.

The S2 findings all cluster around **zeroisation completeness of private-key material on the stack/heap in Rust-side parse and helper paths**. The code's stated discipline — "Signing-key material NEVER touches disk" (sign.rs §8-header) and "InviteSecret zeroises on drop" (invite.rs §wrapper-doc) — is honoured at the final-wrapper boundary but leaks at intermediate copies. None of these are exploitable through a remote vector; they bite only under process-memory dump, core-file capture, or post-free memory reuse by an attacker with already-significant local-access. S2 rather than S1 because the process-memory-disclosure threat is bounded by OS-level protections and operator discipline already in play for `ZETL_CAP_SIGNING_KEY` env-var handling.

The S3 findings are regression-defence hygiene (compile-time `ZeroizeOnDrop` pins on more wrappers), minor ergonomic parsing asymmetries, and one test that will need to flip when SPEC-034 v0.5.0 adopts the Tier 2 S1-01 recommendation to sign envelope headers.

## S2 Findings

### S2-01 — Ed25519 private-scalar residue in signing-key parse chain (`sign.rs::parse_signing_key_b64`, `load_signing_key_from_env`)

**Affected:** `sign.rs:243-264`, `sign.rs:322-327`, module-header zeroisation claim at `sign.rs:40-46`.

**Problem.** The module header advertises zeroisation as a defence:

> "[`VaultSigningKey`] wraps [`ed25519_dalek::SigningKey`], which implements [`zeroize::ZeroizeOnDrop`] under the default feature set. The wrapper deliberately withholds `Debug`/`Display`/`Clone` so a stray `{:?}` or accidental copy cannot leak the private scalar into a log line or a stack frame."

The `SigningKey` itself zeroes on drop (ed25519-dalek 2.2.0 default features include `zeroize`). But the **parse chain** that produces the `SigningKey` makes three residual copies of the raw 32-byte private scalar that are **not** zeroed:

```rust
// sign.rs:322-326 — load_signing_key_from_env
let raw = env::var(ZETL_CAP_SIGNING_KEY_ENV)... // String on heap, not Zeroized

// sign.rs:248-253 — parse_signing_key_b64
let raw = STANDARD.decode(trimmed)...?;        // Vec<u8> on heap, not Zeroized
...
let mut bytes = [0u8; SIGNING_KEY_LEN];        // stack [u8;32], not Zeroized
bytes.copy_from_slice(&raw);
Ok(VaultSigningKey::from_bytes(&bytes))
```

At `Ok` return:
- The heap `String` from `env::var` (which contains the base64-encoded private scalar — reversible to raw bytes in one pass) drops, deallocates, but the underlying allocator buffer is returned to the allocator **without** being overwritten.
- The heap `Vec<u8>` from `STANDARD.decode(...)` (which contains the raw 32-byte private scalar verbatim) drops, deallocates the same way.
- The stack `[u8; 32]` named `bytes` drops; its storage is stack-frame memory that remains until the next frame reuses it.

None of these are `Zeroize`-typed, so none are overwritten on drop. The private scalar therefore persists in at least three distinct regions of process memory past the parse call.

**Why S2, not S1.** Attacker has to already hold local-process memory-disclosure (core dump, swap file, GDB attach, `/proc/<pid>/mem`). That surface is already broken open by the `ZETL_CAP_SIGNING_KEY` env var existing in `/proc/<pid>/environ` in the first place — so the marginal gap is "how long does the key linger after parse" rather than "does the key exist in memory at all." Still, the module advertises zeroisation; advertising without delivering is worse than not advertising. The `VaultSigningKey` final wrapper *does* zeroise, so the claim is locally-true-but-misleading.

**Recommendation.**

```rust
use zeroize::Zeroizing;

pub fn parse_signing_key_b64(env: &'static str, s: &str) -> Result<VaultSigningKey, KeyLoadError> {
    let trimmed = s.trim();
    if trimmed.is_empty() {
        return Err(KeyLoadError::EnvEmpty { env });
    }
    let raw = Zeroizing::new(
        STANDARD.decode(trimmed).map_err(|e| KeyLoadError::Base64 {
            env,
            detail: e.to_string(),
        })?,
    );
    if raw.len() != SIGNING_KEY_LEN {
        return Err(KeyLoadError::Length {
            env,
            got: raw.len(),
            expected: SIGNING_KEY_LEN,
        });
    }
    let mut bytes = Zeroizing::new([0u8; SIGNING_KEY_LEN]);
    bytes.copy_from_slice(&raw);
    Ok(VaultSigningKey::from_bytes(&bytes))
}
```

And for `load_signing_key_from_env`, wrap the env-var read:

```rust
pub fn load_signing_key_from_env() -> Result<VaultSigningKey, KeyLoadError> {
    let raw = Zeroizing::new(
        env::var(ZETL_CAP_SIGNING_KEY_ENV).map_err(|_| KeyLoadError::EnvMissing {
            env: ZETL_CAP_SIGNING_KEY_ENV,
        })?,
    );
    parse_signing_key_b64(ZETL_CAP_SIGNING_KEY_ENV, raw.as_str())
}
```

Add a test that demonstrates the pattern: `use Zeroizing<Vec<u8>>` verified at compile time via `fn _assert_raw_is_zeroized() { fn takes<T: ZeroizeOnDrop>(_: &T) {} /* compile-time check */ }`. Regression defence similar to `pad.rs::ephemeral_padding_secret_is_zeroize_on_drop`.

Note: `Zeroizing<String>` does exist; it zeroes the buffer on drop. `env::var` returns an owned `String`; wrapping at the call site is a one-line change.

### S2-02 — Invite-secret stack-residue in `invite::xor_split_private_key` and `generate_invite_keypair`

**Affected:** `invite.rs:120-133` (generate), `invite.rs:144-163` (xor_split).

**Problem.** The module advertises `InviteSecret` as the safe boundary — a wrapper that `#[derive(ZeroizeOnDrop)]`s the inner `[u8; 32]`. That claim holds at the wrapper level. But two helpers around it make stack-local copies of the raw scalar that are **plain `[u8; 32]`**, not `Zeroizing`/`ZeroizeOnDrop`, and are **not** explicitly zeroed:

**(a)** `generate_invite_keypair` (line 123):

```rust
let sk = StaticSecret::random_from_rng(&mut *rng);
let pk = PublicKey::from(&sk);
let mut priv_bytes = [0u8; 32];
priv_bytes.copy_from_slice(&sk.to_bytes());  // to_bytes() returns [u8; 32] by value
drop(sk);
InviteKeypair {
    secret: InviteSecret { inner: priv_bytes },
    public: *pk.as_bytes(),
}
```

`StaticSecret::to_bytes()` in x25519-dalek 2.0.1 returns `[u8; 32]` by value — a fresh copy of the inner scalar. That returned value is an **unnamed temporary** borrowed by `copy_from_slice` and then dropped without zeroisation. Its 32 bytes persist in the caller's stack frame until the frame is reused.

`priv_bytes` is then moved into `InviteSecret.inner`, which *is* zeroized-on-drop — so that storage is protected. But the stack slot that held `priv_bytes` **before** the move-to-field is itself a plain `[u8; 32]`; post-move, the bytes may or may not be memcpy'd depending on optimisation (the compiler frequently elides the move), but the conservative cryptographic posture is "assume the bytes stayed on the stack until overwritten."

**(b)** `xor_split_private_key` (line 148):

```rust
pub fn xor_split_private_key<R: RngCore + CryptoRng>(
    secret: InviteSecret,
    rng: &mut R,
) -> (String, String) {
    let priv_bytes = *secret.as_bytes();  // ← STACK COPY, not Zeroizing
    let mut half2 = [0u8; 32];
    rng.fill_bytes(&mut half2);
    let mut half1 = [0u8; 32];
    for i in 0..32 {
        half1[i] = priv_bytes[i] ^ half2[i];
    }
    let half1_b64 = URL_SAFE_NO_PAD.encode(half1);
    let half2_b64 = URL_SAFE_NO_PAD.encode(half2);
    half1.zeroize();
    half2.zeroize();
    drop(secret);
    // ← `priv_bytes` is dropped here WITHOUT being zeroized
    (half1_b64, half2_b64)
}
```

`priv_bytes` is explicitly the raw 32-byte X25519 private scalar. It's copied out of `InviteSecret` (which zeroes on drop) into a plain stack array that is **never** zeroed. `half1` and `half2` ARE zeroed — the code clearly knows the pattern — but `priv_bytes` was missed. This is the most directly fixable gap in the whole crypto surface.

**Why S2.** Same threat-model bounds as S2-01: requires local-process memory disclosure. The `InviteSecret` wrapper's whole reason for existing (`"Zeroed on drop so a panic between key generation and URL render cannot leak bytes to the heap"` — module doc line 76) is specifically to prevent this class of leak; the wrapper then leaks **through its own helpers** with no heap or panic involved.

**Recommendation.**

```rust
use zeroize::Zeroizing;

pub fn xor_split_private_key<R: RngCore + CryptoRng>(
    secret: InviteSecret,
    rng: &mut R,
) -> (String, String) {
    let priv_bytes = Zeroizing::new(*secret.as_bytes());  // drops with zero
    let mut half2 = Zeroizing::new([0u8; 32]);
    rng.fill_bytes(&mut *half2);
    let mut half1 = Zeroizing::new([0u8; 32]);
    for i in 0..32 {
        half1[i] = priv_bytes[i] ^ half2[i];
    }
    let half1_b64 = URL_SAFE_NO_PAD.encode(&*half1);
    let half2_b64 = URL_SAFE_NO_PAD.encode(&*half2);
    drop(secret);
    (half1_b64, half2_b64)
}
```

And for `generate_invite_keypair`, minimise the temporary exposure by moving through a `Zeroizing<[u8; 32]>`:

```rust
pub fn generate_invite_keypair<R: RngCore + CryptoRng>(rng: &mut R) -> InviteKeypair {
    let sk = StaticSecret::random_from_rng(&mut *rng);
    let pk = PublicKey::from(&sk);
    // x25519-dalek returns a fresh [u8; 32]; wrap so any residual copy
    // in the move-chain is zeroed.
    let priv_bytes: Zeroizing<[u8; 32]> = Zeroizing::new(sk.to_bytes());
    drop(sk);
    InviteKeypair {
        secret: InviteSecret { inner: *priv_bytes },
        public: *pk.as_bytes(),
    }
}
```

The unnamed-temp from `sk.to_bytes()` itself is still a plain `[u8;32]` on the stack briefly — unavoidable without x25519-dalek API changes. Wrapping in `Zeroizing` immediately minimises exposure.

Add a post-condition test via `Zeroizing`-wrapping probe: there is no easy way to literally observe stack residue, but a compile-time bound `fn _xor_split_locals_are_zeroizing() { ... }` that constructs a `Zeroizing<[u8;32]>` in the same shape would catch a regression where someone un-wraps back to plain `[u8;32]`.

### S2-03 — Header-tampering invariant is codified in a test, locking in Tier 2 S1-01 finding at impl level

**Affected:** `sign.rs:660-689` (`header_tampering_does_not_invalidate_signature`), `sign.rs:16-22` + `sign.rs:351-365` (CON-3404 comment + wire-format doc).

**Problem.** The implementation faithfully realises CON-3404: "The Ed25519 signature covers the bytes of the age ciphertext only (excluding the envelope headers)." The test `header_tampering_does_not_invalidate_signature` explicitly **pins that a tampered `Zetl-Cohort-Id` still yields a verifying envelope**:

```rust
let parsed = parse_envelope(&tampered).expect("parses — headers unauthenticated");
assert_eq!(parsed.header.cohort_id, "attackerxxx");
// Signature still verifies over the original ciphertext bytes.
verify_ciphertext(&key.verifying_key(), &parsed.ciphertext, &parsed.signature)
    .expect("header tamper leaves signature intact");
```

The **companion** Tier 2 review (S1-01 at `.hence/reviews/cap-tier2-2026-04-20.md:49-78`) flagged unsigned envelope headers as a blocker at the spec level: `Zetl-Cohort-Id` and `Zetl-Cohort-Mode` drive shim dispatch, so an attacker able to mutate them (trivially — any CDN middle-box can) can pivot to UX-confusion attacks and a phishing scaffold even without decryption. The spec-level mitigation is to extend the signed byte-range to cover (canonicalised) envelope headers, or AEAD-protect them.

**Why this is a code-review-level S2.** The test does not merely *not reject* tampered headers — it **asserts that tampering is tolerated**. When SPEC-034 v0.5.x adopts the Tier 2 S1-01 recommendation, this test will need to be **inverted** (the exact same tampering case must now be `Err(VerifyError::Invalid(_))`). A passing test named `header_tampering_does_not_invalidate_signature` is a calcification risk: future contributors will read the test as "this is how it's supposed to work" and resist the spec amendment. The comment at line 662-664 (`"CON-3404: ...headers exist for dispatch, not authentication"`) reinforces the calcification.

This is a pre-existing spec decision; the impl is correct against the current spec. I flag it as S2 because **the test name and its passing condition will silently outlast the spec amendment** unless someone remembers to update it. The safest move is to annotate the test with a `TODO: SPEC-034 v0.5.0 + Tier-2 S1-01 — invert to expect VerifyError::Invalid` comment now, while the context is fresh.

**Recommendation.**

Option A (minimum-change): add a `TODO(SPEC-034-v0.5-S1-01)` comment to the test body and a corresponding note in the module header (`sign.rs:18-22`) pointing at `.hence/reviews/cap-tier2-2026-04-20.md:49-78`. Current behaviour preserved; next spec iteration has a breadcrumb.

Option B (defence-in-depth, independent of spec decision): add a parallel `SignedEnvelope` API with an opt-in sign-headers flag. Callers can transition page-by-page. The pure-core remains back-compat; new pages get the wider signed range.

Option C (align with Tier 2 recommendation pre-emptively): invert the test now and extend `sign_ciphertext` to take a `&EnvelopeHeader` and sign a canonical `H(header) || ciphertext` composition. This is the v0.5.0-level change and is too ambitious for this task's scope, but worth tracking in a follow-up task before the Tier 1 review unblocks a broader crypto-code merge to main.

At minimum, **Option A is strongly recommended as part of this merge** — one comment, one line. Anything less bakes in the v0.4 posture indefinitely.

## S3 Findings

### S3-01 — `VaultSigningKey` and `InviteSecret` lack compile-time `ZeroizeOnDrop` regression pins

**Affected:** `sign.rs:98-100` (`VaultSigningKey`), `invite.rs:80-83` (`InviteSecret`).

`pad.rs` has a compile-time bound:

```rust
fn assert_zeroize_on_drop<T: ZeroizeOnDrop>() {}
#[test]
fn ephemeral_padding_secret_is_zeroize_on_drop() {
    assert_zeroize_on_drop::<EphemeralPaddingSecret>();
}
```

This pattern is the spec's "verifiable discard" guarantee (ADR-3413). Neither `VaultSigningKey` nor `InviteSecret` have equivalent pins:

- `VaultSigningKey { inner: SigningKey }` does not `#[derive(ZeroizeOnDrop)]`. Its zeroisation is load-bearing on `SigningKey`'s own `ZeroizeOnDrop` impl, which is itself load-bearing on ed25519-dalek's `zeroize` default feature. A future `Cargo.toml` line of the form `ed25519-dalek = { version = "...", default-features = false, features = ["rand_core"] }` — e.g., during a "slim build" refactor — would silently break the zeroisation guarantee without any test noticing.
- `InviteSecret` *does* `#[derive(ZeroizeOnDrop)]` (line 80), but no test asserts the marker. A derive-macro typo (`ZeroizeOnDrop` → `Zeroize`, which is a different trait) would compile and test-pass while losing the drop-time zero.

**Recommendation.** Add to `sign.rs` tests:

```rust
fn assert_zeroize_on_drop<T: ZeroizeOnDrop>() {}
#[test]
fn vault_signing_key_is_zeroize_on_drop() {
    assert_zeroize_on_drop::<VaultSigningKey>();
}
```

This requires adding `#[derive(ZeroizeOnDrop)]` to `VaultSigningKey` (safe — `SigningKey` is `ZeroizeOnDrop`). Same pattern for `invite.rs`:

```rust
fn assert_zeroize_on_drop<T: ZeroizeOnDrop>() {}
#[test]
fn invite_secret_is_zeroize_on_drop() {
    assert_zeroize_on_drop::<InviteSecret>();
}
```

Three tests total, all compile-time bounds; near-zero runtime cost; catches feature-flag regressions and derive-macro typos.

### S3-02 — Private-key parse accepts only STANDARD base64 while pubkey parse accepts both alphabets

**Affected:** `sign.rs:243-264` vs `sign.rs:276-304`.

`parse_signing_key_b64` (private) decodes only with `STANDARD`:

```rust
let raw = STANDARD.decode(trimmed).map_err(...)?;
```

`parse_signing_pubkey_b64` (public) tries both:

```rust
let raw = URL_SAFE_NO_PAD
    .decode(trimmed)
    .or_else(|_| STANDARD.decode(trimmed))
    .map_err(...)?;
```

This asymmetry is intentional per the docstring on `parse_signing_pubkey_b64` ("Operators who copy either form into `recipients.toml` should not be greeted with a parser surprise") — but the justification applies equally to the private key. `ztl cap genkey` emits STANDARD base64 for both (line 337 in genkey.rs). If a future tool — JSON stringification of a key, for example — emits URL_SAFE_NO_PAD for the private key too, the operator gets a base64 decode error instead of a successful parse.

**Recommendation.** Mirror the pubkey's both-alphabets logic in `parse_signing_key_b64`:

```rust
let raw = STANDARD
    .decode(trimmed)
    .or_else(|_| URL_SAFE_NO_PAD.decode(trimmed))
    .map_err(|e| KeyLoadError::Base64 { env, detail: e.to_string() })?;
```

Strictly additive; no caller breaks.

### S3-03 — `derive_path_cap` HKDF `info` relies on upstream cohort-id validator for collision-safety

**Affected:** `derivation.rs:99-104` (info construction), `recipients/parsing.rs:219-226` (cohort-id validator).

`derive_path_cap` builds the HKDF `info` as:

```
"ztl/path-cap/v1/" || cohort_id || "/" || slug
```

Tier 2 S3-01 flagged length-prefixing as the safer construction. The code is currently collision-safe **only because** `is_valid_cohort_id` in `recipients/parsing.rs` restricts `cohort_id` to `[a-z0-9][a-z0-9-]*` — no `/`. The derivation module comments this (`derivation.rs:94-98`):

> "Callers that pass slashes or other delimiters in cohort_id/slug are responsible for escaping upstream; the validator in `cap::grants::validation` restricts cohort_id to `[a-z0-9][a-z0-9-]*` so no ambiguity enters here."

The comment references the **wrong module** (the validator lives in `cap::recipients::parsing`, not `cap::grants::validation`; the latter validates grants.toml, not recipients.toml cohort ids). The invariant is correct but documented loosely — "the validator in `cap::grants::validation`" would return `None` to a grep-based regression check.

More importantly: a length-prefix is cheap, survives validator regressions, and matches the cryptographic hygiene Tier 2 S3-01 recommends. Suggested form:

```rust
// info = tag || u16_be(len(cohort_id)) || cohort_id || u16_be(len(slug)) || slug
let mut info = Vec::with_capacity(
    PATH_CAP_INFO_PREFIX.len() + 2 + cohort_id.len() + 2 + slug.len(),
);
info.extend_from_slice(PATH_CAP_INFO_PREFIX.as_bytes());
info.extend_from_slice(&(cohort_id.len() as u16).to_be_bytes());
info.extend_from_slice(cohort_id.as_bytes());
info.extend_from_slice(&(slug.len() as u16).to_be_bytes());
info.extend_from_slice(slug.as_bytes());
```

**Wire-format break warning.** This changes path-cap derivation for every existing cohort, so any cohort that has shipped URLs must rotate. This is precisely why the concern is S3, not S2: the collision-safety *is* preserved by the validator; the recommendation is about defence-in-depth against regression of a separate module. Defer to v0.5.x if at all; do not push into this merge.

Minimum-change for this merge: fix the cross-reference comment at `derivation.rs:97` to point at `cap::recipients::parsing::is_valid_cohort_id`. One-word edit.

### S3-04 — Tail-bit zeroisation in Crockford base32 for non-5-bit-multiple path-caps

**Affected:** `derivation.rs:153-177` (`crockford_encode`).

`crockford_encode` pads the tail bits with zero-fill:

```rust
if bits > 0 {
    let idx = ((buf << (5 - bits)) & 0x1f) as usize;
    out.push(CROCKFORD_ALPHABET[idx] as char);
}
```

For the 48-bit path-cap (10 chars × 5 bits = 50 bits encoded, 2 zero-fill bits) the trailing character uses only 3 meaningful bits — it can only be one of 8 values. For the 64-bit path-cap (13 chars × 5 bits = 65 bits, 1 zero-fill bit) the trailing character can only be even-indexed values. Character-level frequency distribution is skewed at the tail.

**Why S3 only.** Path-cap bits are treated as a URL identifier, not as an encryption key or authentication token. There is no decoder. The "entropy" is `path_cap_bits` bits exactly, with zero lost — the Crockford representation merely renders those bits in a non-uniform last-character distribution. A distinguisher would need the full 48/64/128-bit pre-image to observe the pattern, at which point they already have the path-cap. No vulnerability; noting only as a test-data consideration: if anyone writes a property test that sample-distributes path-cap last characters uniformly, it will fail.

**Recommendation.** No code change. Add a comment above `crockford_encode`:

> "Tail bits short of a full 5-bit group are zero-filled. For 48-bit input the 10th character uses 3 meaningful bits; for 64-bit input the 13th character uses 4 meaningful bits; for 128-bit input all 26 characters use 5 meaningful bits. This is an encoding artefact, not an entropy loss — the preimage bits are preserved exactly."

### S3-05 — `generate_grant_id` consumes 8 bits of RNG output per 5 bits of Crockford character

**Affected:** `invite.rs:190-200`.

```rust
for _ in 0..GRANT_ID_RANDOM_CHARS {
    let mut b = [0u8; 1];
    rng.fill_bytes(&mut b);
    let idx = (b[0] & 0x1f) as usize;
    buf.push(CROCKFORD_ALPHABET[idx] as char);
}
```

26 chars × 8 bits = 208 bits of RNG state consumed for 130 bits of output. Efficiency wart, not a security issue — OsRng (ChaCha-backed) is essentially free. The upper 3 bits of each byte are discarded; under a uniform byte source the remaining 5 bits are uniform over `[0,31]`, so the grant-id body is uniformly distributed in Crockford space.

**Recommendation.** If a future refactor introduces rate-limited entropy (HSM, low-throughput hardware RNG, constrained-device build), reuse each byte: pack 8 bytes into a 64-bit integer and emit 12 characters from that (5×12=60 bits per 8-byte read), then top up with a short second read. No action for this merge.

let mut diff: u8 = 0;

### S3-07 — `encode_age_recipient` bech32-round-trip is fragile against `age` version bumps

**Affected:** `age_encrypt.rs:177-180`.

```rust
fn encode_age_recipient(pk: &X25519Pubkey) -> String {
    let hrp = Hrp::parse("age").expect("hrp \"age\" is a valid bech32 hrp");
    bech32::encode::<Bech32>(hrp, pk).expect("32 bytes fits inside bech32 length limit")
}
```

The docstring (line 34-44) explains the round-trip:

> "`age::x25519::Recipient` exposes no public constructor from a raw `[u8; 32]` in 0.11 — only `FromStr` on the `"age1…"` bech32 string. We therefore encode each pubkey (real or padding) into the canonical age1 form with the standard `Bech32` variant (HRP `"age"`) and `parse::<age::x25519::Recipient>()` it."

`encode_age_recipient_matches_age_crate_bech32` pins the round-trip (line 346-357). But:

1. The `expect()` calls assume the bech32 encoding never fails for a 32-byte payload. That is true for the standard `Bech32` variant under the HRP `"age"` — the `bech32` 0.11 crate has a max-payload-length of 90 chars, and 32 bytes + HRP + checksum + separator = 65 chars. Safe.
2. If `age` ever changes its canonical form (e.g., `age1p...` → `age2p...` in age v2), the round-trip parse will fail at runtime with `AgeEncryptError::RecipientParse`. Current test coverage is only the "happy path" where both ends agree. A future age version would break the test and the build, which is correct — but the error path is one we'd only find out about on upgrade, not before.
3. If `age` gains a public `Recipient::from_bytes(&[u8; 32])` constructor, this whole function can go. A `TODO(age)` comment tracking that would help.

**Recommendation.** Add a `TODO` comment:

```rust
// TODO(age): remove this bech32 round-trip once `age::x25519::Recipient`
// exposes a public `from_bytes(&[u8; 32])` constructor (age >= 0.12?).
// Upstream tracking: <add age repo issue link if opened>.
fn encode_age_recipient(pk: &X25519Pubkey) -> String { ... }
```

No code change required.

### S3-08 — `parse_envelope` accepts unknown headers (forward-compat) without size cap

**Affected:** `sign.rs:470-477`.

```rust
_ => {
    // Forward-compat: unknown headers are tolerated so a
    // newer builder adding a hint-header does not break
    // older verifiers. ...
}
```

Good forward-compat discipline. But the parser's outer structure (`for line in header_text.split('\n')`) has no cap on the number of header lines or the size of the header region. The `header_text` is bounded only by the position of the first `\n\n` separator. A hostile envelope with a 100 MiB header block preceding the age ciphertext would be silently accepted into the parser, at O(n) allocation cost (the parser holds `header_bytes` by reference, good — but `header_text.split('\n').collect()` would materialise every line, and each unknown line is a `(name, value)` split-once).

In practice: the envelope ingestion path reads the whole file into `bytes: &[u8]`, so the cap is "how much memory does the caller give the parser." For build-time self-verification this is fine (`bytes` = the just-encrypted file; bounded by the vault's own page size). For the shim parsing a CDN-served envelope, the caller is noble-ed25519 / the shim harness — not this parser.

**Why S3.** Not exploitable through the shim (JS parser is separate, bounds presumably enforced at `fetch` level). Not exploitable through Rust build (bytes are the vault's own output). But `parse_envelope` is exported; a future effectful-shell path that verifies externally-delivered envelopes would inherit the uncapped-header gotcha.

**Recommendation.** Add a sanity cap:

```rust
pub const MAX_HEADER_REGION_BYTES: usize = 4096;

pub fn parse_envelope(bytes: &[u8]) -> Result<ParsedEnvelope, EnvelopeParseError> {
    let search_limit = bytes.len().min(MAX_HEADER_REGION_BYTES);
    let sep = bytes[..search_limit]
        .windows(2)
        .position(|w| w == b"\n\n")
        .ok_or(EnvelopeParseError::MissingSeparator)?;
    ...
}
```

6 headers × ~80 bytes = ~500 bytes for the current CON-3404 wire format; 4 KiB is an 8× cushion that still rejects nonsense header blocks.

### S3-09 — `sign_and_build_envelope` has no sanity check on envelope-header field contents

**Affected:** `sign.rs:382-389`, `render_header` line 391-422.

`render_header` concatenates `header.cohort_id`, `header.slug`, `header.build_epoch` into the wire format without any validation that they don't contain `\n` or `: ` — which are the wire-format delimiters. A caller who passes `cohort_id = "eng\nZetl-Signature: AAAA"` would produce an envelope with a **spoofed signature header embedded in the cohort-id line**. The parser would then see two `Zetl-Signature:` header lines and take the last one (the malicious one) because the `match name { ... }` arm overwrites `signature_b64`.

**Why S3, not S2.** All current call sites pass already-validated strings:
- `cohort_id` is validated by `is_valid_cohort_id` at recipients.toml parse.
- `slug` is taken from the vault file name, which is filesystem-constrained.
- `build_epoch` is formatted by `format_rfc3339_utc`, which emits a fixed `YYYY-MM-DDThh:mm:ssZ` format.

So no current caller can construct a malicious `EnvelopeHeader`. But `EnvelopeHeader` is **pub** with all fields **pub** — a downstream caller (test harness, future CLI, integration test) could construct one from an untrusted source and the wire format would escape-inject silently.

**Recommendation.** Validate in the builder:

```rust
fn render_header(header: &EnvelopeHeader, sig_b64: &str) -> String {
    // Defense-in-depth: reject header-field delimiters in values.
    // All current call sites already filter these; this belt-and-braces
    // catches a downstream caller who forgets.
    for (name, val) in [
        (HEADER_COHORT_ID, header.cohort_id.as_str()),
        (HEADER_SLUG, header.slug.as_str()),
        (HEADER_BUILD_EPOCH, header.build_epoch.as_str()),
    ] {
        debug_assert!(
            !val.contains('\n') && !val.contains(": "),
            "envelope header {name} field contains a delimiter: {val:?}"
        );
    }
    ...
}
```

`debug_assert!` only fires in tests/dev builds; release is unaffected. Release-time validation would require turning `render_header` into a fallible function and threading the error through `sign_and_build_envelope` — bigger change, defer.

Alternative: make `EnvelopeHeader` fields `pub(crate)` with getters, and enforce validation in a `new()` constructor. More invasive; better hygiene long-term.

### S3-10 — `ParsedSecret::Debug` redacts but does not mark `#[deny(Display)]`; future `Display` derive would leak

**Affected:** `genkey.rs:153-167`.

`ParsedSecret`'s `Debug` implementation is hand-rolled to redact the random body and checksum. Good. But a future maintainer adding `#[derive(Display)]` or an `impl Display for ParsedSecret` would compile without warning and leak the full decoded secret. /// use ztl::cap::genkey::ParsedSecret;
/// fn _display_is_forbidden(p: &ParsedSecret) -> String { format!("{p}") }

```

Cheap regression defence.

### S3-11 — RFC 5869 test vector is present; other NIST test-vector coverage absent

**Affected:** `derivation.rs:296-313`.

The RFC 5869 Appendix A.1 HKDF-SHA-256 test vector is wired in. Good. No equivalent test vector for:

## Not-a-Finding Notes (positive)

Items I scrutinised and found adequate:

- **`verify_strict` is the right choice over `verify`.** RFC 8032 §5.1.7 strict canonical verification rejects non-canonical R/S and small-order A. Test `verify_ciphertext_rejects_non_canonical_signature` pins the choice.
- **Padding scalar discard.** `EphemeralPaddingSecret` wraps `StaticSecret` under `#[derive(ZeroizeOnDrop)]`; the wrapper is explicitly `drop`'d inside the generation loop (not at end-of-scope). The compile-time bound `ephemeral_padding_secret_is_zeroize_on_drop` makes the guarantee load-bearing on the type system. This is the cleanest piece of the crypto surface.
- **`CryptoRng` trait bound on padding generation.** `pad_to_tier_with_rng<R: RngCore + CryptoRng>` prevents accidentally passing a non-cryptographic RNG. The comment at `pad.rs:108-112` explains why. Good defence against a future refactor.
- **`SigningKey::ZeroizeOnDrop` via ed25519-dalek's default features.** The Cargo.toml line `ed25519-dalek = { version = "2", features = ["rand_core"] }` keeps the default features on (including `zeroize`). The `SigningKey` inner field of `VaultSigningKey` therefore zero-izes on drop. (S3-01 flags that this guarantee is not pinned by a compile-time test — good to add, but the guarantee itself holds.)
- **Tier-ladder values + `MAX_REAL_RECIPIENTS`.** `TIERS = [10, 30, 100, 300, 1000]` and `MAX_REAL_RECIPIENTS = 1000` exactly match REQ-3422. The `tier_for` function uses `.find(|&t| t >= real_count)` — correct-by-construction for the ascending ladder. Every tier boundary is tested (`tier_for_covers_each_bucket_boundary`).
- **HKDF `info` string separation.** `ztl/path-cap/v1/...`, `ztl/tofu-wrap/v1`, `ztl/hardened-identity/v1` are three distinct byte strings with a consistent namespace prefix and explicit versioning. `wrap_key_deterministic_and_distinct_from_identity` pins the separation.
- **Determinism guarantees.** `sign.rs::signatures_are_deterministic`, `pad.rs::deterministic_with_seeded_rng`, `derivation.rs::derive_path_cap_deterministic`, `genkey.rs::seeded_generation_is_reproducible`. Every pure-core function is probed for reproducibility under a fixed seed. Good SPEC-034 §8 compliance.
- **`age::Encryptor::with_recipients` failure surfacing.** Even though the current age 0.11 only rejects empty recipient lists (which we prevent by always padding to ≥ 10), the `AgeEncryptError::Encrypt` variant is kept as a belt-and-suspenders surface for upstream changes. Comment at `age_encrypt.rs:90-95` is honest about this.
- **`header_stanzas_are_all_x25519` byte-level check.** Not library-level; scans the age-v1 ASCII header for `-> X25519 ` prefixes and asserts exactly `tier` are present, plus rejects `-> scrypt ` and `-> ssh-`. Catches a refactor that accidentally switches recipient type. This is the right level of test for REQ-3422 acceptance #3.
- **Grant-id entropy.** 26 Crockford chars × 5 bits = 130 bits. Comfortable collision margin for any realistic operator-grant volume (2^65 grants before 50% collision probability). Efficiency gripe in S3-05 is not a security concern.
- **XOR-split correctness.** `half1 = priv ⊕ half2` with `half2` fresh from CSPRNG. Each half is uniform-random when viewed in isolation. Test `xor_split_halves_xor_back_to_priv` pins the reconstruction. The concern flagged by Tier 2 S2-03 (that `second_factor = "spoken-phrase"` cannot carry 256 bits) is a **spec-level** concern about what gets put in `half2` — at the code level, `xor_split_private_key` correctly samples a full 32-byte `half2`. If the operator pipes that 43-char base64 string through a voice call, the resulting transcription error rate is the operator's problem; the cryptographic XOR is right.
- **No logging of secrets.** Grep across `src/cap/{sign,pad,derivation,age_encrypt,genkey,invite}.rs` for `println!`, `eprintln!`, `tracing::`, `log::` shows **zero** key-material log lines. Error paths render remediation hints (`"re-run \`ztl cap genkey\`"`) but never the offending bytes. `SecretParseError` variants carry env-var names and length details, never raw bytes. `ParsedSecret::Debug` is hand-rolled to redact. This is the cleanest no-log discipline I could ask for.
- **`rand_core::OsRng` provenance.** `rand_core 0.6.4` with `features = ["getrandom"]`. On Linux, `getrandom(2)`; on macOS, `CCRandomGenerateBytes`; on Windows, `BCryptGenRandom`. All CSPRNG-backed. No `thread_rng` use anywhere in the crypto paths. Good.
- **Signature byte-range = age ciphertext only.** Consistent across `sign_ciphertext`, `build_envelope`, `sign_and_build_envelope`, `verify_ciphertext`, and the test matrix. `ciphertext_tampering_invalidates_envelope_signature` + `sign_and_verify_round_trip` pin the range from both directions. (The **spec-level** concern that the range is too narrow to cover dispatch headers is the Tier 2 S1-01 finding; S2-03 above flags the calcification risk at the impl level.)
- **Cohort-salt bytes vs text.** The effectful shell (`main.rs:11716-11717`) samples 32 bytes from OsRng, base64url-encodes them, and persists the text form. Subsequent builds read the text back and pass `cohort_salt_stable.as_bytes()` (~43 chars) into HKDF-Extract as salt. HKDF-Extract accepts arbitrary salt; the composition is self-consistent. Entropy is 256 bits delivered as ~43 bytes of salt input — fine. Slightly unusual; not wrong.
- **Crockford alphabet.** `0123456789ABCDEFGHJKMNPQRSTVWXYZ` — no `I`/`L`/`O`/`U`. Matches the intent to avoid transcription confusion. Grant-id test `generate_grant_id_shape` asserts charset membership.
- **Error-message remediation.** Every parse error points the operator at `ztl cap genkey` (or the spec) as the remediation. Byte-stable integration tests (per the task's dev log) presumably pin these.

## Cross-Cutting: PRF Salt / Hardened-Mode Identity — What Is in Rust, What Is Not

The task brief calls out "WebAuthn PRF salt construction." The Rust code surface contains:

- `HARDENED_IDENTITY_INFO = b"ztl/hardened-identity/v1"` (derivation.rs:46)
- `TOFU_WRAP_INFO = b"ztl/tofu-wrap/v1"` (derivation.rs:42)
- `derive_tofu_wrap_key(prf_output: &[u8]) -> [u8; 32]` (derivation.rs:123)
- `derive_hardened_identity_seed(prf_output: &[u8]) -> [u8; 32]` (derivation.rs:141)

These are the **second half** of the PRF chain — HKDF-Expand of the `prf_output` with distinct `info` strings for the two roles. Both `info` strings are versioned (`/v1`), cross-role-distinct, and exercised together in `wrap_key_deterministic_and_distinct_from_identity` (derivation.rs:259-265) which asserts they produce **different** outputs from identical IKM.

The **first half** of the chain — the PRF salt itself, `SHA-256("ztl/webauthn-prf/v1/" || rp_id || "/" || cohort_id)` — has **no Rust-side implementation**. It lives in the shim (JS). A Rust review can only confirm:

- The `prf_output` consumed here is documented as the opaque output of WebAuthn's `prf.results.first`. The HKDF step that follows is a pure function of that output plus the role-discriminating `info`.
- The two role outputs are proven distinct (`assert_ne!(a, c, ...)`) given identical IKM.

If the shim's PRF salt composition is wrong (e.g., Tier 2 S3-01's length-prefixing concern or rp_id-vs-origin ambiguity), that error propagates into `prf_output` and the Rust HKDF step is powerless to catch it. The separation of concerns is correct — Rust owns the HKDF-Expand step and proves the role-separation property; the shim owns the PRF-Eval + its salt composition.

No Rust-side change recommended. Tier 2 S3-01 is the canonical place to address the shim-side concern.
