## Self-review findings

Severity definitions per
[`PROTO-001`](../../handbook/engineering/usdd-agent-protocol.md#severity-vs-priority):
S1 critical, S2 major, S3 moderate, S4 minor.

### S2 — OIDC session method-tag attribution

`OidcAuthenticator::authenticate()` abstains (file: `src/web/auth/oidc.rs`).
An OIDC-minted session cookie is consequently observed by the
`PasskeyAuthenticator` cookie path (always-present in the default chain),
which tags the principal `method = "passkey"` in the audit trail.

**Impact:** the audit log cannot distinguish OIDC-originated sessions
from passkey-originated sessions. Operator forensic queries that depend
on this attribution (e.g. "show me every OIDC login by alice@example.com
in the last 30 days") get wrong answers.

**Resolution path:** `SessionStore` needs to remember the mint method
(small enum field on `Session`). Each authenticator's cookie validation
path then returns the recorded method, not its own. Estimated ~50 LOC +
4 tests.

**Currently mitigated by:** documented gap in `docs/collab-auth.md` and
the SPEC-041 §13 Phase 6 commit message. Operator-log line at mint time
(in the callback handler) still records `method=oidc`, so a careful
operator could correlate. Not sufficient for an automated query.

### S3 — Extractor cookie parsing not migrated

`SessionUser`, `SessionRole`, `BearerUser`, `AuthUser` in
`src/web/session.rs` still parse cookies/Bearer headers internally
(documented in the gate-refactor commit). The acceptance bar for
task-auth-gate-refactor wanted "no raw-header parsing outside `auth/*`."

**Impact:** mild duplication. The principal extension IS set by
`auth_resolve` and the gates DO consume it; the extractors only
additionally parse the cookie to expose `SessionUser.token` (used at
`src/web/routes.rs:262` for CSRF lookup). The extractors agree with the
principal extension on auth decisions — there's no divergence — but the
code paths are duplicated.

**Resolution path:** split the extractors. `SessionUser` becomes a thin
reader of the extension; a separate `SessionCookie` extractor exists
solely for handlers that need the raw cookie token (logout, CSRF
lookup).

**Status:** documented as a deferred follow-up in the gate-refactor
commit. The deferral is intentional — migrating the extractors is a
mechanical refactor that does not change auth behaviour.

### S3 — Login-redirect order under multi-method-with-redirects

If `methods = ["passkey", "password", "oidc"]` and a browser hits an
unauthenticated content route, `collab_gate` redirects to
`/auth/login` (the passkey login). The other methods' `login_redirect`
values (`Some("/auth/password")`, `Some("/auth/oidc/login")`) are not
consulted.

**Impact:** operators who want password OR OIDC to be the primary
browser login surface must order their methods accordingly and either
remove `passkey` or accept the passkey-first behaviour.

**Resolution path:** `collab_gate` could pick the first
`login_redirect()` from the chain instead of hardcoding
`/auth/login`. Spec §15 lists this as an open question.

**Currently mitigated by:** documentation. The operator-facing guide
notes that the FIRST redirect-capable method in `methods` should be
the intended browser login surface. Not yet enforced by code.

### S3 — Mock-IdP integration test deferred

`oidc.rs` ships pure unit tests (10 tests covering URL building, PKCE
challenge, pending-state TTL + single-use, sub-discriminator, config
parsing, redirect-URI derivation). The end-to-end mock-IdP test
(spinning up an axum-based fake discovery + JWKS + token endpoint) is
deferred.

**Impact:** the IO shell (discovery fetch, code exchange, JWKS fetch)
is not exercised by tests — only the pure validation pieces are. Live
testing against a real IdP is straightforward but has not been
performed in this session.

**Resolution path:** new test file
`tests/oidc_mock_idp_integration.rs` (~200 LOC) that spins up an axum
server serving the OIDC discovery + JWKS + token endpoints with
operator-controlled token contents. Tested matrix: happy path,
bad `state`, wrong `aud`, wrong `nonce`, expired token, replayed
`state`, missing `user_id_claim`. Spec acceptance for TEST-4109/4110
explicitly names this.

### S3 — REQ-4120 LangSec coverage gaps (operator-channel input)

REQ-4120 says "every contract in §7 that accepts external input declares
a formal grammar and recognises input fully before any semantic action."
CON-4109 declares the cap-token grammar; the `?cap=` query is parsed by
`extract_cap_query_value` which is permissive (strips `&`, finds the
`cap=` prefix). The cap-token grammar is enforced downstream (the JWT
recogniser fails on malformed tokens), so an ungrammatical `cap=` value
yields Abstain — not a per-grammar reject. **Acceptable in spirit but
not literal.**

CON-4108 declares the proxy-header value grammar; `recognise_user_value`
enforces it strictly (reject, not normalise). **Acceptable.**

CON-4105 declares the password form-body grammar; `recognise_form_body`
enforces it strictly. **Acceptable.**

CON-4102 declares the `[collab.auth]` schema; `parse` + `validate` use
`deny_unknown_fields`. **Acceptable.**

CON-4104 declares the OIDC callback-query grammar; the implementation
uses axum's `Query<CallbackQuery>` which is permissive (accepts unknown
params silently). **Gap** — a strict recogniser would reject unknown
params. Practical impact: a malicious IdP-mixup attempt could land
unexpected params on the callback; the unknown params are ignored
rather than rejected. Mitigated by `state` single-use + signature
checks. **Recommend:** swap `Query<CallbackQuery>` for a hand-written
strict recogniser in a future task.

### S4 — `format_chain_summary` doesn't list per-method config status

The OBS-4105 startup line lists method names and compiled features but
not which methods are misconfigured. A typo in `[collab.auth.oidc]
client_secret_file` (file does not exist) fails startup with a useful
error, but a missing `provision_domain_allow` when `auto_provision =
true` is currently caught only when the first OIDC login runs (since
`provision_domain_allow` is `Option`). **Recommend:** `validate()`
catches this at startup.

### S4 — Capability mint registry doesn't auto-prune

`zetl collab share list` shows expired tokens forever (status is
computed from current time at list time). The mint registry
(`.zetl/collab/cap-shares.json`) grows monotonically. Not a security
issue — expired tokens never authenticate — but the file grows
unbounded. **Recommend:** lazy GC of records past their `exp` on every
`record_mint` write.

## Addendum 2026-05-15 — fresh-context security-review pass

A `/security-review` skill (fresh agent context, no access to this
session's reasoning trace) was run against the PR. Two findings cleared
the ≥8-confidence filter; both have been fixed in this branch:

* **Vuln 1 (High) — post-OIDC-login open redirect.** Source: `?next=`
  query in `oidc.rs::login_handler` was stored verbatim and emitted
  through `Redirect::temporary` at the callback with no validation.
  **Fix:** new `safe_return_to` helper restricts the redirect target to
  same-origin local paths (must start with single `/`, reject `//` and
  `/\` protocol-relative shapes). Applied at BOTH the input
  (login_handler — bad values never enter pending state) and the sink
  (callback — load-bearing). 2 new unit tests cover the allow/deny
  matrix.

* **Vuln 2 (Medium) — path traversal via unsanitised `user_id`.**
  `ensure_user` → `save_profile` → `vault_root.join(".zetl/users").join(user_id)…`;
  `Path::join` does not normalise `..`, so a `user_id = ".."` from
  either OIDC's `user_id_claim` or a malformed `X-Forwarded-User`
  resolves to `vault_root/.zetl/profile.json`. **Fix:** new
  `is_safe_user_id` guard at the top of `ensure_user` rejects empty,
  over-length (>256), separator-containing, NUL-containing, and the
  exact `.`/`..` literals before any filesystem read — closing both the
  create-profile escape and the load-profile sibling-read. Defence in
  depth: `proxy_header::recognise_user_value` also rejects the exact
  `.` and `..` literals at the recogniser layer. 3 new tests
  (`is_safe_user_id` matrix, `ensure_user_rejects_dotdot_before_io`
  regression, `ensure_user_rejects_path_traversal_shapes`).

* **Vuln 3 (Confidence 7, originally below the report threshold —
  fixed anyway as defence in depth).** `capability_gate` allowed paths
  whose components include `..` or `.` because globset's `**` matches
  `/` and `.`. Downstream page_handler uses a slug HashMap lookup that
  404s on `..`-containing slugs (so no exploit through the page route),
  but `try_serve_public` (active when the operator runs `serve --public
  <dir>`) resolves `..` via OS path semantics — a real traversal sink
  conditional on operator config. **Fix:** new
  `path_has_traversal_segment` helper rejects `.` / `..` segments in
  both raw and percent-encoded form (handles `%2e%2e` and case
  variants that the literal split would miss because axum's
  `Uri::path()` returns the percent-encoded path). Applied at the gate
  before the globset match so the capability's authority is unambiguous
  regardless of how downstream code handles path normalisation. 1 new
  matrix unit test + 2 new full-pipeline integration cases (raw `..`
  and percent-encoded `%2e%2e`).

Cross-context review's "not a finding" notes (alg-confusion via JWT
header, OIDC `OnceLock` config-overwrite, CSRF exemption via stateless
principal) were confirmed as non-vulnerabilities — see the review
record for the specific verified safety properties.

Findings unaddressed (same as the original self-review section above):
the OIDC session method-tag S2, the four extractor S3s, the OIDC
callback strict-recogniser S3 (REQ-4120 literal compliance), the
login-redirect ordering S3, and the mock-IdP integration test S3.

This addendum does NOT replace the cross-model Tier-1 review (PROTO-001
Principle 12 still requires a different model family from the producer);
it records that the fresh-context same-model security pass found two
concrete vulns, both now fixed and regression-tested.
